LadybugDB vs Neo4j

Neo4j invented the property-graph market. But if you're shipping agents, edge deployments, or per-tenant graphs, do you still want a server cluster with GPL/commercial licensing? LadybugDB is DuckDB for graphs: embedded, columnar, Cypher-compatible, MIT.

TL;DR verdict

Keep Neo4j for large shared clusters, GDS algorithms, and Bloom tooling. Choose LadybugDB for embedded/serverless, columnar analytics, MIT embedding, zero-ops cost, and agent-native OpenAPI/MCP. Most Cypher ports directly.

Cost & license: the real decider

Neo4j Community's GPL restricts commercial embedding; production teams land on Enterprise or Aura — per-core or consumption billing that grows with every tenant. LadybugDB's MIT license lets you ship the engine inside your product (legal-tech, medical, finance) with no per-seat meter, plus optional enterprise support when you need an SLA.

The JVM tax: why Java was the wrong foundation

Neo4j runs on the JVM — and you pay for it on every deployment. Gigabytes of heap before storing a single node. Garbage-collection pauses injecting tail-latency spikes into traversals that should be microseconds. Slow cold starts, mandatory heap tuning (-Xmx roulette), and a runtime that fights containers, edge devices, and serverless instead of disappearing into them. Object headers and pointer-heavy record layouts bloat every node and edge versus a packed columnar layout.

LadybugDB is native C++: a zero-dependency binary that embeds in-process with deterministic latency, minimal footprint, and no runtime to babysit — the DuckDB playbook applied to graphs. Because it is just C++, it runs on a range of devices competitors can't follow: WASM in the browser, native iOS and Android, and any architecture with a C compiler — from laptops to phones to edge boards. Your graph goes where your users are, not where the server room is. Compiled languages (C++ here, Rust elsewhere) hold a structural advantage in embedded environments: predictable performance, tiny binaries, and memory you spend on your graph, not on the runtime's bookkeeping. The JVM made sense for enterprise middleware in 2007. It is overhead you should no longer accept in a database.

Ecosystem edge: Icebug, icebug-format, and NetworkX go columnar

Neo4j's GDS library is mature — but it lives behind the cluster wall, on a row store, under a commercial license. LadybugDB answers with an open ecosystem bet:

  • Icebug: a columnar fork of NetworKit shipping 220+ graph algorithms (centrality, community detection, paths, embeddings) that run directly on LadybugDB's CSR data — no export, no second engine, no license meter.
  • icebug-format: open Parquet-with-CSR storage. Your graph lives in the lakehouse (Iceberg tables + icebug-disk graphs = GraphLake) and stays readable by every Parquet/Arrow tool. No proprietary store-in.
  • NetworkX goes columnar too: the same ideas are reaching Python's most popular graph library via the nx-arrow and nx-ladybug backends — larger-than-RAM, columnar-backed graphs in plain NetworkX code. Learn once, scale everywhere.

Migration: Neo4j → LadybugDB

  1. Export: apoc.export.csv.* or Parquet dumps of nodes + edges.
  2. Re-create schema: CREATE NODE TABLE Person(name STRING, PRIMARY KEY(id)) — then COPY ... FROM.
  3. Port Cypher: most MATCH/WHERE/RETURN, aggregations, and variable-length paths work as-is. Replace APOC/GDS-specific procedures with app code or LadybugDB equivalents.
  4. Repoint drivers: swap Bolt for the ladybugdb Python/JS package or OpenAPI; agents can use the MCP server directly.
// Runs on both Neo4j and LadybugDB
MATCH (p:Person)-[:TRANSFERRED_TO*2..5]->(q:Person)
WHERE p.riskScore > 0.8
RETURN p.name, q.name, length(shortestPath((p)-[*]->(q))) AS hops
LIMIT 100
